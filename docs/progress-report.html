Part 1 · What stands out

  • The risk model is now real and honest. architecture_risk_scores() returns Option per category and accumulates an unknown_metrics list; total_score stays null unless every required category is known. This is exactly the “don't fabricate a zero” discipline the confidence model was always reaching for, now enforced in one tested function.
  • Artifact freshness is tracked. read_artifact() distinguishes missing / stale / unreadable / available and compares artifact mtime against source mtime (artifacts.rs:134), feeding meta.summary.artifact_status and map confidence. Stale inputs can no longer silently score a module.
  • Git history is derived from one git log --numstat pass and bucketed to modules, with defect-keyword detection and co-change counting — a clean, dependency-free implementation.
  • The docs were corrected in both directions. The clone-analysis section was honestly downgraded from the previous “--engine all” claim to “token signals only; a future syntax-backed engine should report its own confidence” — which sets up Part 2 nicely.
  • Cargo target discovery got safer and narrower: only top-level files under tests/benches/examples are cataloged, so nested fixture crates (like this repo's own tests/fixtures/*) are no longer miscounted as the package's tests.

Part 1 · Residual & new items

R1 · ast_hasher is the new unused helper Low

Deleting leverage_ast closed finding 2, but rust_helpers/src/bin/ast_hasher.rs is now an unused helper in the same position — a full syn binary that nothing invokes (a repo-wide search finds no caller). The difference is that it is explicitly labelled “Experimental … Reserved for AST clone analysis,” so this is intentional scaffolding rather than forgotten code. It is the subject of Part 2 — the recommendation is to wire it in or keep it clearly fenced, not to delete it.

R2 · The helper crate now has zero tests Low

The unit tests that used to live beside leverage_ast went with it, and ast_hasher ships untested. cargo test --manifest-path rust_helpers/Cargo.toml reports 0 tests. The extractor (rust_facts) is the most semantically dense code in the project and is currently exercised only end-to-end through the CLI fixtures. A few direct parse_file-based unit tests on the visitor (escape counting, complexity, module-file resolution) would localize regressions.

R3 · Extraction still shells out via cargo run Nit

RunContext removed the repeated extraction, which was the real cost. What remains is that each surviving extraction call still goes through cargo run --bin rust_facts (facts.rs:167), paying a Cargo freshness check per invocation. Building the helper once and invoking the binary directly would shave the last bit of startup overhead, and parsing files with rayon inside the helper remains an easy win on large targets. Optional.

Part 2 · Clone detection — opportunities to improve

The current detector (clones(), producers.rs:390) is a single token engine: it tokenizes each file line-by-line with a regex, normalizes identifiers to ID and integer literals to LIT (keeping a small keyword/punctuation set), slides a fixed 50-token window across the stream, groups windows whose normalized token sequence is byte-for-byte identical, and (newly) drops overlapping windows per file before emitting groups of ≥2. That is a solid, deterministic Type-1 / normalized-Type-2 detector. The opportunities below are ordered by value-to-effort.

C1 · Wire in the AST engine that already exists High value

Observation

The output schema already carries an "engine": "token" discriminator, the catalog historically promised AST clone analysis, and ast_hasher already computes a per-function, name-insensitive, literal-normalized structural hash. Yet clones() never calls it, so only one engine ever runs.

Why it matters

The token engine groups only on identical normalized sequences, so it cannot see two functions that are structurally the same but differ in formatting, statement order, or interleaved comments. A function-level AST engine catches exactly that class (Type-2 with reordering, near Type-3), which is where the highest-value refactor candidates usually hide.

Direction

  • Run ast_hasher from RunContext (it reuses the same paths file machinery), group functions by ast_hash, and emit engine: "ast" rows alongside the token rows.
  • Per the project's own docs, give AST rows confidence_scope: "syntax_facts" (they depend on the helper) while token rows keep source_scan — so a parse failure correctly degrades only the AST layer.

C2 · The AST hasher is currently too loose and too narrow High value

Observation

Before wiring it in, two correctness issues in ast_hasher.rs need attention:

  • Too narrow: it only walks top-level file.items for Item::Fn (ast_hasher.rs:104). Methods inside impl blocks and functions in nested mods — i.e. most real code — are never hashed. It should use a Visit that records every ItemFn and ImplItemFn, as rust_facts already does.
  • Too loose: the structural hash mixes in only std::mem::discriminant of each Expr/Stmt (ast_hasher.rs:40-50). Two functions with the same shape of statements collide regardless of operators, called methods, or paths — so a + function and a - function hash equal. With no minimum node-count guard, every trivial getter collides too, flooding results with noise.

Direction

  • Incorporate discriminating detail into the hash: binary/unary operator kind, method-call identifiers, path tails, and literal kinds — while still normalizing identifier names and literal values so Type-2 clones survive.
  • Skip functions below a minimum node/statement count (e.g. < 6 nodes) to suppress getter/setter noise, and emit that node count so scoring can weight by clone size.

C3 · Use a stable hash for persisted AST identities Medium

Observation

ast_hasher uses std::collections::hash_map::DefaultHasher (SipHash with a library-defined seed). The token engine, by contrast, uses the project's own FNV stable_hash(). DefaultHasher's output is explicitly not guaranteed stable across Rust versions or runs.

Why it matters

The moment an ast_hash is written into clones.json and compared across machines or over time (which is the whole point of a portable measurement artifact), an unstable hash produces spurious churn and breaks cross-run diffing.

Direction

Hash with the same FNV-1a routine used by stable_hash() (or any fixed-seed hasher) so identities are reproducible.

C4 · The fixed 50-token window is rigid and crosses item boundaries Medium

Observation

tokens.windows(50) slides one global window across the whole file's token stream. Two consequences: (a) clones meaningfully shorter or longer than ~50 tokens are reported at a fixed, misleading length — token_count is even hardcoded to 50 in the output; and (b) a window can straddle the end of one function and the start of the next, manufacturing a “clone” that is really two unrelated fragments that happen to abut.

Direction

  • Short term: reset the window at item boundaries (don't let a window span two functions), and report the actual matched token length rather than the constant 50.
  • Longer term: replace fixed windows with maximal-match detection — build a suffix automaton / suffix array over the normalized token stream and report longest repeated token runs above a threshold. This yields true clone lengths and finds both short and long duplicates in one pass.

C5 · Tokenizer is line-oriented and string/comment-blind Medium

Observation

Tokenizing line-by-line with a regex means the contents of string and char literals and the text of comments are tokenized as if they were code — e.g. a string literal "if x { }" contributes if and brace tokens. This is the same class of issue the hotspots producer just moved away from by going AST-backed, but the token clone path still has it.

Direction

Either lex with a Rust-aware tokenizer (proc-macro2's token stream, available in the helper) so strings/comments are single opaque tokens, or normalize whole string/char literals to a single STR token. This reduces false positives from comment blocks and string tables.

C6 · Scoring ignores clone size and noise class Low

Observation

score = instance_count × 5 (producers.rs:473) treats a tiny 3-line same-file repeat the same as a large cross-file duplication of equal instance count, and applies no floor to filter boilerplate (repeated use blocks, derive-shaped field lists, match-arm scaffolding).

Direction

Fold clone size and cross-file spread into the score (e.g. instances × matched_tokens × cross_file_factor), and expose a minimum-tokens / minimum-lines threshold (config-driven) to cut trivial repeats. Attach risk_model_id/risk_calibration as the other scored producers do, so the clone score is traceable to a calibration table like the rest of the model.

C7 · Memory: full snippets are materialized for every window Low

Observation

Each of the (very many) sliding windows stores a reconstructed multi-line snippet string in the windows map before filtering to groups of ≥2 (producers.rs:441). On a large tree this is a large transient allocation, almost all of which is discarded.

Direction

Key the first pass on a rolling hash of the normalized window and store only (file, start, end); reconstruct snippets lazily for the surviving groups. A rolling hash also removes the per-position join("|") of 50 tokens.
