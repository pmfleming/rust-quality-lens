rust-quality-lens — Code Review

Improvement opportunities & observations · reviewed 2026-06-02 · commit 4e0d7bb (master)
Summary. rust-quality-lens is a well-shaped, single-purpose tool: a Rust CLI (rqlens) that emits portable JSON measurements (hotspots, clones, escape hatches, type health, locality, leverage, correctness, architecture map), backed by a syn fact-extractor helper. The command/artifact contract is clean, the confidence model is a genuinely good idea, and the golden-fixture approach is sound. The most valuable improvements are not bugs but drift: documentation that describes a richer scoring engine than the code actually implements, an entire unused helper binary, and a per-producer subprocess model that re-parses the whole tree several times. None of the items below require the tool to change its public contract.

1. Documentation describes scoring the code does not implement High

What I found

docs/risk-model-v1.md and docs/measurement-upgrades.md document a substantially richer engine than src/main.rs actually contains. Concretely, the docs reference machinery that exists nowhere in the codebase (confirmed by a full-repo search — these strings appear only inside the docs):

  • A shared architecture_risk_scores(...) function. measurement-upgrades.md states “Architecture map scoring now calls the shared architecture_risk_scores(...) function instead of carrying local weight math.” No such function exists. architecture_map() in src/main.rs:1012 carries local math: architectural = (outbound*10 + inbound*8).min(300), and sets change_risk, correctness_risk, and total_score to null, performance_risk to a hardcoded 0.0.
  • Change / correctness / performance scoring. risk-model-v1.md specifies detailed weights for churn, commit count, contributors, defect-keyword commits, benchmark mean/variance, layer violations, and cycle-membership penalties. None of these are computed — there is no git history ingestion, no benchmark ingestion, and no layer-violation or cycle detection in the code.
  • meta.summary.artifact_status and unknown-module counts. Both docs promise a map-level summary reporting unknown metrics and artifact status. The architecture_map() output has no summary key at all.
  • slowspots.json performance facts. Referenced as an input in risk-model-v1.md; never produced or consumed.
  • README plurality. README.md says “Syntax-aware facts come from helper binaries” (plural), but only rust_facts is invoked (see finding 2).

Why it matters

This is the highest-leverage issue precisely because the tool's entire purpose is to be a trustworthy measurement source for a downstream dashboard. Documentation that overstates the model erodes exactly the trust the confidence-field design works so hard to build. A consumer reading risk-model-v1.md will expect change_risk and total_score to be populated and meaningful.

Suggested direction

Split the docs into “implemented v1” vs. “planned”. Move the git/benchmark/layer-violation weights and the architecture_risk_scores / artifact_status / slowspots descriptions into a clearly-labelled roadmap section, and have risk-model-v1.md describe only what map.json actually emits today (the flat outbound/inbound architectural score and the unknown_metrics nulls). Alternatively, if the richer model is the real target, the docs become a spec to implement against — either way, close the gap explicitly.

2. The leverage_ast helper binary is dead code High

What I found

rust_helpers/src/bin/leverage_ast.rs is a complete syn-based visitor (heap-vs-inline type ratios, iterator-vs-for-loop leverage, unsafe surface, scoring, and its own unit tests). But the CLI's leverage() producer at src/main.rs:980 computes leverage purely from the module dependency graph (68.0 + inbound*2.5 - outbound*3.0) and never invokes this binary. A repo-wide search confirms leverage_ast is referenced only by its own file — main.rs only ever spawns the rust_facts bin.

Why it matters

An entire compiled binary with tests is shipped but unreachable. It compiles on every helper build, carries its own (subtly divergent) copy of module_key_for_path that ignores RQLENS_SOURCE_ROOTS, and creates a strong false impression that AST-level leverage metrics are part of the output. The leverage_metrics.json a consumer receives contains graph reach/pressure, not the indirection-ratio / iterator-leverage signals this file computes.

Suggested direction

Decide its fate explicitly: either wire leverage_ast into the leverage producer (the richer signals look more useful than raw fan-in/fan-out, and would justify the “binaries” plural in the README), or delete it. Leaving it half-connected is the worst of both.

3. Fact extraction re-runs and re-parses the tree once per producer Medium

What I found

rust_facts_for_paths() (src/main.rs:467) shells out to cargo run --bin rust_facts and re-parses every file. In a single measure all run it is invoked independently by escape_hatches, type_health, correctness, and by module_graph() — which is itself called separately by locality, leverage, and map. That is on the order of six full passes over the same source tree per run, each paying cargo dispatch overhead plus a complete syn re-parse, with no caching of the resulting FileFacts.

Why it matters

Cost scales linearly with the number of producers for no analytical gain. On a large target project the repeated parse dominates wall-clock time, and the work is trivially shared because every producer keys off the same source_roots.

Suggested direction

  • Compute FileFacts once at the start of a multi-tool run and pass the slice into each producer (the data structures are already shared between main.rs and the helper).
  • Invoke the prebuilt helper binary directly rather than cargo run each time, so dispatch and the up-to-date check happen once.
  • The helper already iterates files independently — parsing them with rayon would be a cheap further win on large trees.

4. Hotspots complexity is substring matching on raw text Medium

What I found

hotspots() (src/main.rs:794) derives cognitive/cyclomatic complexity with count_matches(&text, &[" if ", " match ", " for ", ...]) over the file's raw text. This counts keyword-shaped substrings inside string literals, comments, and identifiers, and depends on exact surrounding spaces (e.g. "&&", "?" match anywhere, while " if " misses if not flanked by spaces). The token clones producer goes to the trouble of tokenizing and normalizing, and the project already has a full syn AST in the helper — so hotspots is the one producer working against the grain of the rest of the design.

Why it matters

Complexity is the headline “quality_score” and the map's maintainability input. Counting ? and || inside doc comments or string literals inflates it unpredictably, which undercuts the “trustworthy measurement” goal and contradicts the docs' claim that the major measurements are syn-backed.

Suggested direction

Move branch/decision counting into the rust_facts visitor (it already walks if, match, loops, and ? as AST nodes) and emit per-file complexity facts, leaving hotspots to do only scoring. If a pure-text fallback is intentional (for files that fail to parse), document that and gate it on parse_status.

5. Attribute names leak into the dependency graph Medium

What I found

In the helper, scan_attrs() (rust_helpers/src/bin/rust_facts.rs:159) calls self.add_dependency(path) for every attribute path it encounters — so derive, cfg, test, repr, allow, etc. all enter the dependencies vector. Similarly visit_expr_path, visit_path, and visit_type_path each push path strings, producing heavy over-collection.

Why it matters

resolve_dependency() later filters candidates against known module keys, so most noise is dropped — but a project with a module literally named test, used, or derive would pick up phantom edges, skewing locality, leverage, and the architecture map. It is also wasted allocation on every file.

Suggested direction

Don't feed attribute-path identifiers into dependencies — attributes are already handled for their specific escape-hatch signals. Restrict dependency collection to use trees, call/type paths, and explicit module references.

6. Process-wide set_current_dir as control flow Medium

What I found

measure() (src/main.rs:196) does env::set_current_dir(&config.project_root), runs all producers against relative paths, then restores the old cwd in a closure. Producers and helpers then rely on the ambient cwd (e.g. Path::new("Cargo.toml"), iter_rust_files on relative roots).

Why it matters

Mutating the process-global working directory is implicit, non-reentrant, and unsafe under any future threading. If a producer panics, the closure-based restore is bypassed (panics unwind past it), leaving the process in the wrong directory. It also makes the code harder to reason about because path resolution depends on hidden global state rather than on config.project_root.

Suggested direction

Thread project_root through path construction (join roots onto it explicitly) instead of changing the cwd. If that is too large a change short-term, at least restore the cwd via a guard type with a Drop impl so it survives panics.

7. Scoring logic has no unit tests; several producers lack coverage Medium

What I found

src/main.rs contains no #[cfg(test)] module at all. The scoring and resolution functions that encode the actual model — type_risk, over_free, resolve_dependency (with its crate::/self::/super:: handling), escape-hatch weighting and the Clippy de-duplication, and the hotspots formula — are exercised only indirectly, if at all. The integration suite (tests/cli.rs) covers catalog, type-health, map, correctness, hotspots-confidence, and clones-confidence, but not the escape-hatches, locality, or leverage outputs, cross-file clone grouping, or correctness-run. Only leverage_ast (the dead binary) has dedicated unit tests.

Why it matters

The model weights and thresholds are the product. Without unit tests, a tweak to a weight or a refactor of resolve_dependency can silently change every downstream score, and the golden fixtures only catch a narrow slice.

Suggested direction

Add pure-function unit tests for resolve_dependency (each prefix form), over_free /type_risk boundaries, and the escape-hatch Clippy/lint de-duplication. These are deterministic and cheap. Extend the integration suite to assert on at least one escape-hatch and one leverage row.

8. Helper binaries duplicate path/module logic with no shared crate Low

What I found

normalize_path, module_key_for_path, failed_record, the -h/--help + single-argument parsing, and the read/parse loop are copy-pasted between rust_facts.rs and leverage_ast.rs. The two copies of module_key_for_path have already diverged: rust_facts honors RQLENS_SOURCE_ROOTS, leverage_ast does not.

Why it matters

Divergent duplicates are a maintenance trap — a fix applied to one extractor silently misses the other, exactly as the RQLENS_SOURCE_ROOTS divergence demonstrates.

Suggested direction

Promote rust_helpers to a small library crate with the two binaries depending on it, hoisting the shared path/module/arg helpers. (Moot for leverage_ast specifically if finding 2 resolves to deletion.)

9. Silent read failures and a partial_cmp().unwrap() panic surface Low

What I found

  • hotspots, clones, and architecture_map read source with fs::read_to_string(&path).unwrap_or_default() (e.g. src/main.rs:798, :1027). An unreadable file is silently treated as empty — it still counts toward the file total in the confidence model, so the output reports complete: true while having measured nothing for that file.
  • Every producer's sort uses partial_cmp(...).unwrap() on f64 scores (e.g. src/main.rs:849). If any score is NaN (reachable if an upstream count ever yields a NaN through round2), the sort comparator panics.

Why it matters

Both are low-probability but both undermine the confidence guarantees: one hides missing data behind a “complete” flag, the other turns a data anomaly into a crash rather than a degraded measurement.

Suggested direction

Record read failures as a confidence signal (a stale_input/missing_input entry) rather than defaulting to empty. Use total_cmp for f64 sorting, or push NaN to the bottom deterministically.

10. Cargo manifest is regex-scraped instead of parsed Low

What I found

correctness_paths() (src/main.rs:1302) extracts test/target paths from Cargo.toml with the regex ^\s*path\s*=\s*"([^"]+\.rs)". The crate already depends on toml and deserializes rqlens.toml with it.

Why it matters

A line-oriented regex is blind to TOML structure: it would match a path = "….rs" key in any table (including a hypothetical path dependency), and miss anything not formatted on one line. It is more fragile than the parser already in the dependency tree.

Suggested direction

Deserialize the relevant [[bin]]/[[test]]/[[bench]]/[[example]] target tables with toml and read their path fields structurally.

11. Monolithic main.rs and minor cleanups Nit

What I found

  • src/main.rs is ~1,750 lines holding CLI parsing, config, all eight producers, the risk model, the layer classifier, and IO helpers. docs/extraction-notes.md already flags “split the Rust CLI into smaller modules” as the next step — worth acting on, e.g. producers/, model.rs, graph.rs, facts.rs.
  • clones() stores a full (path, start, end, snippet) tuple for every 50-token window of every file in a HashMap before filtering to groups of ≥2 (src/main.rs:891). On a large tree this is a lot of transient memory; the snippet could be reconstructed lazily for surviving groups only.
  • "token_count": 50 is emitted as a literal even though it always equals the hardcoded window width — fine, but tie it to the constant so the two can't drift.
  • MeasureTool repeats its name strings across name() and the #[value(name=)] attributes; a single source of truth would prevent skew.

Why it matters

Pure maintainability — none affect output today.

What's already good

  • The measurement-confidence model (source-scan vs. syntax-facts scopes, explicit missing_input/unsupported_pattern) is a genuinely strong design that most quality tools lack.
  • Raw counts are kept separate from scoring counts (e.g. the Clippy/lint de-duplication in escape_hatches preserves raw evidence while adjusting the score) — exactly the right instinct for a versioned model.
  • Golden + mini fixtures make the intended extraction behavior executable and regression-resistant.
  • Cross-platform path handling is careful and consistent (normalize_slashes, RQLENS_SOURCE_ROOTS, absolutize/resolve helpers).
  • Clean separation of concerns at the product level: the lens emits JSON only and deliberately leaves the dashboard to a sibling repo.
